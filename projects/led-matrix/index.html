8×8 LED Music Visualizer

Sixty-four LEDs driven from sixteen pins by scanning the grid faster than the eye can follow — then wired to an audio input so the display reacts to music in real time, running an FFT on an 8-bit microcontroller.

Overview

Built for ENGR40M at Stanford across two projects: first the display itself, then making it respond to sound.

The display starts as a pin-budget problem. Lighting 64 LEDs individually would need 64 outputs and the board does not have them, so the LEDs are wired as an 8×8 grid — eight anode rows, eight cathode columns, sixteen pins total. The cost is that arbitrary LEDs can no longer be lit simultaneously, so the display is time-multiplexed: one row is energised at any instant, scanned fast enough that the eye integrates the frames into a steady image.

The second half turns it into an instrument. Audio from a phone or laptop is fed into the microcontroller's analog-to-digital converter, and a fast Fourier transform splits the signal into frequency bands, so the grid can show what the music is actually made of rather than just how loud it is.

What is inside

  • Stanford Metro Mini (Arduino Uno compatible)
  • 64 LEDs in an 8×8 grid
  • Current-limiting resistors (100-150 Ω)
  • pMOS transistors for row drive
  • 3.5 mm audio jack
  • PAM8302A 2.5 W Class D amplifier
  • 8 Ω speaker
  • 0.1 µF capacitor + 2×220 kΩ (biasing network)
  • Custom red PCB / protoboard

How it was built

Matrix wiring

Eight anode pins and eight cathode pins address the grid: an LED lights only when its row is driven high and its column pulled low. In firmware those are two arrays — ANODE_PINS on digital 13 down to 6, and CATHODE_PINS spanning A3-A0 and digital 5 down to 2, using the analog pins as ordinary digital outputs.

Scanning and persistence of vision

The display loop walks one row at a time, sets the column pattern for that row, holds briefly, then moves on. Any single LED is dark most of the time, but at a high enough refresh the image looks continuous rather than flickering.

Current limiting

Each column gets a series resistor sized so the LED sits at a sane operating point rather than at whatever the supply will deliver. Simulation put the branches around 12-18 mA at roughly 1.85 V across the diode, using 100 Ω, 110 Ω and 150 Ω resistors on the modelled columns.

Row drive transistors

An I/O pin can source enough current for one LED, not for a whole row at once. pMOS transistors sit between the supply and each anode row so the microcontroller only has to switch a gate, while the transistor carries the row current.

Getting audio into the ADC

The Metro Mini has six 10-bit analog inputs, giving values from 0 to 1023 against a 5 V reference. Audio can't be connected straight to one: an audio signal swings either side of zero, and the converter cannot see anything below 0 V, so half of every waveform would be clipped away. A biasing network fixes this — a 0.1 µF series capacitor blocks the DC while passing the audio, and a pair of 220 kΩ resistors from the supply sets the resting point at 2.5 V, centring the signal in the middle of the input range.

FFT and frequency bands

Amplitude alone only tells you how loud the music is. Running a fast Fourier transform — via the openmusiclabs ArduinoFFT library, since an 8-bit microcontroller has no FFT hardware — decomposes each captured window into frequency components, reduced to four bins running from bass to treble. A bass hit drives the low bin high, a cymbal drives the top one, and the grid is driven from those values.

Amplifier and speaker

Signal straight off an audio jack is far too weak to drive a speaker, so a PAM8302A 2.5 W Class D amplifier sits between the jack and an 8 Ω speaker. The board plays the music it is visualising rather than needing a separate source in the room.

What was tricky

  • Audio cannot be fed straight into the converter. An audio signal swings either side of zero and the ADC cannot see below 0 V, so without a biasing network the entire negative half of every waveform is silently clipped away and the visualisation is wrong in a way that still looks plausible.
  • The scan rate has to clear the flicker threshold. Slow it down and the multiplexing stops being invisible — the image breaks into visibly strobing rows instead of a steady picture.
  • Brightness is a side effect of duty cycle here. Each row is only lit for a fraction of the frame, so the display is dimmer than the same LEDs driven continuously, and any time spent on other work in the loop steals from that fraction.

What I learned

  • A constraint can be more productive than more resources. Sixteen pins for sixty-four LEDs forces multiplexing, and multiplexing is what makes the display programmable as a frame buffer rather than as sixty-four separate outputs.
  • Persistence of vision is an engineering budget, not a curiosity. The refresh rate is a real design parameter traded against how much computation fits between frames.
  • Microcontroller pins switch logic, they do not deliver power. Putting transistors between the supply and each row is the same idea as the H-bridge in the useless box — the processor decides, something else carries the current.
  • The frequency domain answers a different question than amplitude. Reading the raw signal tells you how loud the music is; running an FFT tells you what it is made of, and only the second one gives a display worth watching.
