Useless Box

A box whose only function is to switch itself off. Flip the toggle and an arm drives out, flips it back, and retreats — a microcontroller and an H-bridge doing something completely pointless, on purpose.

Overview

Built for ENGR40M at Stanford. The premise is a joke with a real curriculum behind it: the box exists only to undo the one input you can give it, and getting there means driving a motor in both directions from a microcontroller, debouncing physical switches, and structuring the behaviour as a state machine.

The first version of the box is purely electromechanical. This one adds a computer, so the arm's behaviour becomes programmable rather than fixed by wiring — the difference between a circuit that reacts and a system that decides.

What is inside

  • Stanford Metro Mini (Arduino Uno compatible)
  • RFP12N10L power nMOS ×2
  • NDP6020P power pMOS ×2
  • DC gearmotor
  • SPDT toggle switch
  • Limit switch
  • 3×AA battery pack
  • Solderless breadboard
  • Laser-cut acrylic enclosure

How it was built

H-bridge motor driver

The Arduino's I/O pins can't source anywhere near the current a gearmotor needs, so the motor sits inside an H-bridge built from two power nMOS and two power pMOS transistors. Two logic-level inputs from the Arduino select the diagonal pair that conducts, which sets the direction of current through the motor and therefore whether the arm drives out or retracts.

Avoiding shoot-through

The failure mode of an H-bridge is turning on both transistors in one leg at once, shorting the supply straight to ground. Every gate has to be actively driven at all times — an Arduino pin left configured as an input looks like an open circuit and leaves a gate floating, which is enough to switch a transistor on unintentionally.

State machine in firmware

The control logic is a finite state machine implemented as a switch statement inside loop(): read the toggle and the limit switch, decide which state the box is in, and drive the motor outputs accordingly. Structuring it this way keeps the arm's travel, contact, and return phases separate instead of tangled in nested conditionals.

Assembly

Wiring was prototyped on a breadboard and soldered at the switch and motor terminals, then the whole assembly — battery pack, breadboard, gearmotor and toggle — was mounted into a laser-cut acrylic case that leaves the internals visible.

What was tricky

  • An H-bridge fails destructively if both transistors in one leg conduct at once — that path is a dead short from the supply to ground. Every gate has to be driven at all times, and a pin left configured as an input looks like an open circuit, which is enough to let a gate float and switch a transistor on by accident.
  • Because of that, the motor could not simply be wired up and trusted. The driver was verified on its own over serial first, and the switches separately, before either was connected to the state machine.
  • The arm's own limit switch is part of the control loop rather than a safety afterthought — without knowing when the arm has arrived, the firmware has no way to decide when to reverse it.

What I learned

  • Direction is a wiring problem before it is a code problem. An H-bridge makes 'forwards' and 'backwards' a question of which diagonal pair is conducting, so the firmware only ever picks a pair.
  • Test each stage against something you can observe. Driving the bridge from single serial characters, and echoing switch states to the console, made both halves debuggable in isolation — when the whole thing was assembled, any fault had to be in the wiring between them.
  • A finite state machine is worth the ceremony as soon as behaviour has phases. Written as nested conditionals the arm's travel, contact and return would have tangled together; as explicit states each transition is something you can point at.
  • Microcontroller pins are signals, not power. Everything the Arduino does here is switch a gate; the transistors and the battery pack do the actual work of moving the arm.
